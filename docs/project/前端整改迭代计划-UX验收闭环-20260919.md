# 前端整改迭代计划：UX 验收闭环

制定日期：2026-09-19  
目标：将前端从“功能回归通过、体验验收不通过”推进到“比赛演示可用、操作员路径可完成、无障碍门禁基本通过”。

## 一、执行原则

1. 先修会阻断比赛演示和真实操作的 P0，再处理视觉和细节优化；
2. 每次迭代必须有可运行产物、验证命令和人工验收结果；
3. 不以 E2E 全绿替代用户体验验收；
4. 所有权限隐藏、错误、空状态和处理中状态都必须给用户明确反馈；
5. 保留现有业务骨架，不在本轮引入农业、应急、物流等行业特例。

## 二、迭代总览

| 迭代 | 主题 | 主要目标 | 通过门槛 |
|---|---|---|---|
| F0 | 演示运行与权限基线 | 登录、角色、版本、环境标识统一 | 演示账号能稳定进入完整闭环 |
| F1 | 任务主路径 | 任务检查、航线、重规划主动作可完成 | 无死按钮，动作状态可感知 |
| F2 | 告警与详情抽屉 | 告警处置、抽屉焦点、审计反馈统一 | 告警两步内到达下一动作 |
| F3 | 导航与地图可用性 | 导航认知、地图语义和坐标交互优化 | 操作员能稳定定位模块和空间对象 |
| F4 | 表单与机队工作台 | 表单就地校验、飞行器健康状态完善 | 错误可在提交前发现，资源状态可行动 |
| F5 | 全量复验与发布 | 人工验收、自动化回归、材料冻结 | UX 门禁通过，形成发布证据 |

## 三、F0：演示运行与权限基线

### 本次任务

- 固定演示数据库初始化方式，避免持久化账号与启动密码不一致；
- 增加演示账号说明和当前角色显示；
- 对 observer、dispatcher、admin 三种角色分别定义可见功能；
- 设施管理入口不再静默消失，无权限时显示原因和所需角色；
- 左侧版本号、追溯条、页脚环境标签统一从同一运行时元数据生成；
- 登录失败区分“账号错误、服务未启动、数据库不可用、会话过期”。

### 期望产出

- 可重复启动的演示命令；
- 演示账号/角色说明；
- 顶部显示：环境、当前用户、角色、版本、数据边界；
- 设施管理在 dispatcher/admin 下可进入，observer 下有明确权限提示；
- 登录失败可以指导用户下一步处理。

### 验证方式

- 新数据库启动 3 次，均可登录；
- 旧数据库启动 1 次，能提示迁移/密码处理方式；
- 三种角色分别截图并记录菜单、按钮和操作权限；
- 页面所有版本文本一致；
- `npm run test:e2e` 不低于 14/14。

### 通过标准

比赛演示人员不需要修改数据库、不需要猜密码、不需要打开开发者工具，即可进入任务闭环。

## 四、F1：任务主路径

### 本次任务

- 修复“暂无告警但按钮显示查看待处置告警”的死按钮；
- 根据任务状态生成唯一主动作：检查、生成航线、启动飞行、处置告警、查看回放；
- 为检查、航线、重规划、启动飞行增加 idle/loading/success/error 状态；
- 结果面板增加动作来源、执行时间、失败原因和下一步建议；
- 任务列表和详情抽屉使用同一状态定义，避免列表与详情不一致；
- 对 blocked/high/warning/pass 建立统一视觉和文本语义。

### 期望产出

操作员可以按“选任务→检查→航线→异常→重规划→确认→回放”顺序完成，不会遇到无响应按钮或不知道下一步的情况。

### 验证方式

- 计划任务、需处置任务、运行中任务各走一遍；
- 断开 API 或模拟 4xx/5xx，确认错误在按钮附近展示；
- 点击主动作后 300ms 内出现进行中状态；
- 结果面板能追溯规则、数据、引擎版本；
- 新增 Playwright 用例覆盖空告警主动作和失败反馈。

### 通过标准

任意任务从列表进入后，用户始终能看到一个明确且可执行的下一步主动作。

## 五、F2：告警与详情抽屉

### 本次任务

- 顶部优先告警与告警中心复用同一告警卡片，避免重复渲染和重复操作；
- “查看影响”跳转到具体任务/设备/地图对象；
- “标记已处置”增加确认、处置备注、操作人和时间反馈；
- 处置成功后立即更新 OPEN 数量、任务状态和时间线；
- 抽屉打开时焦点进入关闭按钮或标题区域；
- Escape、遮罩点击、关闭按钮均可关闭；
- 关闭后焦点回到触发详情的按钮；
- 长时间线提供摘要、筛选或折叠，避免重复低电量事件淹没关键信息。

### 期望产出

告警处理过程形成清晰闭环：发现→定位影响→执行动作→确认结果→留下审计记录。

### 验证方式

- 至少验证低电量、链路下降、规则阻断三类告警；
- 键盘完成告警查看、处置、关闭；
- 处置后无重复 OPEN 告警；
- 抽屉关闭后焦点恢复到原按钮；
- 屏幕阅读器可读出告警级别、对象、动作和结果。

### 通过标准

任何 P0 告警在两步内到达影响对象和下一步动作，且处置结果可见、可追溯。

## 六、F3：导航与地图可用性

### 本次任务

- 明确采用单页锚点模式，不再制造“假模块切换”；
- 导航点击后同步设置 `aria-current`、聚焦目标标题并显示定位反馈；
- 为态势、任务、规则、机队增加独立模块标题和摘要；
- 地图底图道路、OSM 参考要素默认 `aria-hidden=true`；
- 仅向辅助技术暴露空域单元、设施、飞行器、航线和告警对象；
- 增加地图图层摘要、坐标获取说明和键盘替代路径；
- 统一地图 hover、click、selection 的反馈样式；
- 地图缩放、DEM、居中按钮增加状态文本。

### 期望产出

用户能知道当前所在模块，地图既保留视觉信息，也不会让读屏/键盘用户穿越数百个无关道路节点。

### 验证方式

- 点击四个导航项分别确认滚动、标题聚焦和 active 状态；
- 检查地图可访问性树，只保留业务对象；
- 键盘完成图层开关、地图对象选择和结果查看；
- 验证坐标从“--”变为具体值时有提示；
- MapLibre 和 SVG 两种模式各跑一遍。

### 通过标准

操作员能在 5 秒内定位到目标模块；辅助技术不会被底图噪声阻断。

## 七、F4：表单与机队工作台

### 本次任务

- 增加经纬度范围、时间窗口先后、任务编号唯一性校验；
- 校验失败直接显示在对应字段附近；
- 提交期间禁用按钮并显示“保存中”；
- 飞行器卡片增加链路状态、任务状态、告警状态、最后同步时间；
- 电量使用颜色+文字等级双编码，并明确阈值；
- 飞行器卡片增加明确的“查看详情”入口和键盘焦点样式；
- 设施卡片补充来源、版本、开放时间和容量状态。

### 期望产出

用户可以在提交前发现常见错误，并能从机队工作台判断“哪台设备需要处理、为什么、下一步做什么”。

### 验证方式

- 填写越界坐标、反向时间、重复编号，确认就地提示；
- 模拟慢接口，确认不会重复提交；
- 低电量、离线、执行中、空闲四种飞行器状态各验证一次；
- 键盘完成表单填写和设备详情打开。

### 通过标准

常见输入错误无需等待服务端返回；每台设备都有可读、可操作的状态说明。

## 八、F5：全量复验与发布

### 本次任务

- 执行完整自动化测试、类型检查、构建和静态检查；
- 执行两人角色人工验收；
- 执行桌面、窄屏和键盘路径验收；
- 汇总问题为 P0/P1/P2，并关闭所有 P0；
- 更新截图、演示脚本、版本号和发布清单；
- 形成“问题—修改—验证—证据”对照表。

### 期望产出

- 前端 UX 验收报告更新为“通过”或“条件通过”；
- 比赛演示脚本可按固定顺序重复完成；
- 角色权限、告警、任务、地图、设施和回放均有证据；
- 版本、数据边界、环境标签一致。

### 发布门禁

```powershell
python -m unittest discover -s tests -q
powershell -ExecutionPolicy Bypass -File .\scripts\frontend-static-check.ps1
npm run typecheck:frontend
npm run build:frontend
npm run test:e2e
```

### 最终通过标准

1. P0 问题为 0；
2. P1 问题全部有关闭证据或明确延期理由；
3. 两名队员可独立完成演示主路径；
4. observer、dispatcher、admin 权限表现一致且有解释；
5. 键盘和基本屏幕阅读器路径可完成核心任务；
6. 不能把合成演示数据、离线地图或模拟遥测表述为授权生产数据。

## 九、两人分工

### 队员 A：交互与前端实现

- F0 页面状态、登录反馈、版本与环境标签；
- F1 任务主动作和结果状态；
- F2 告警卡片、抽屉焦点和处置反馈；
- F3 导航、地图语义和响应式交互；
- F4 表单和机队卡片。

### 队员 B：验证与证据

- 维护角色/权限验收矩阵；
- 编写和维护 Playwright 用例；
- 执行键盘、读屏、窄屏和异常接口验证；
- 维护截图、录屏、版本追溯和发布报告；
- 每个迭代结束前出具“通过/不通过/阻断原因”。

## 十、每次迭代结束必须汇报

每次开发结束统一汇报五项：

1. 本次完成了什么；
2. 哪些用户路径已可用；
3. 哪些自动化和人工检查通过；
4. 剩余问题及严重级别；
5. 是否允许进入下一次迭代。
